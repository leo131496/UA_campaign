# 点亮探索局：腾讯生态小游戏 × SCRM 互动获客设计方案

版本：概念方案 v1.0｜日期：2026 年 11 月 21 日

适用场景：品牌／门店拉新；B2B 获客与销售线索培育

拟融合系统：[BesChannels／致趣百川营销云](https://beschannels-stg2.ma.scrmtech.com/dashboard)

## 1. 产品建议

开发「点亮探索局」，以 30–60 秒的翻牌探索作为用户入口，把“内容触达 → 游戏参与 → 兴趣表达 → 自愿领取／预约 → 私域服务 → 核销或销售转化”连接起来。

产品不是独立的游戏流量池，而是 SCRM 内可反复配置、可归因、可承接的互动活动模块。使用一套游戏引擎、两套业务模板：

| 维度 | 品牌／门店模板 | B2B 获客模板 |
| --- | --- | --- |
| 演示名称 | 周末灵感探索局 | 增长灵感探索局 |
| 用户动机 | 找到生活灵感，获得相关体验权益 | 发现增长思路，获得可使用的行动清单 |
| 配对内容 | 咖啡、户外、轻食等生活主题 | 获客—渠道追踪；协同—线索分配；转化—旅程培育 |
| 主动选择 | 用户选填兴趣偏好 | 用户选填当前业务课题 |
| 完成结果 | 兴趣徽章＋权益入口 | 课题徽章＋行动清单入口 |
| 私域承接 | 品牌顾问、门店企微、到店预约 | 行业顾问、企微联系、诊断预约 |
| 业务终点 | 身份可验证的新客、真实核销、复购 | 验证身份、ICP 匹配、销售接受、商机 |
| 分享内容 | “看看你是哪种周末探索家” | “这是我在关注的增长课题，你呢” |

首期聚焦这一个可配置玩法，不同时堆叠大转盘、助力砍价、复杂排行榜和积分商城。

## 2. 已知事实与设计边界

已读取用户提供链接的公开应用入口。页面标题为 BesChannels，描述为“致趣百川一站式营销云”；公开主题样式可见主色 `#FF724F`，入口加载了 Vue 2 与 Element 相关资源。上述信息仅用于判断界面设计的兼容方向，不等于确认项目源代码或内部架构。

目前没有读取登录后的客户、租户菜单、业务配置或 API 文档。本文中的菜单位置、接口、字段、自动化能力和 SSO 方式均为**建议设计或待确认事项**，不代表该租户已具备相应能力。演示页未登录、未写入该系统。

当前交付为浏览器中可运行的交互原型，不是已经上线的微信小程序、微信小游戏包或正式 SCRM 插件。

## 3. 设计理念

### 3.1 先让用户获得价值，再请求必要信息

匿名进入即可玩，兴趣选择可以跳过，完成后直接看结果。用户决定领取权益或预约时，才进入必要的身份关联与授权流程。仅为了看结果，不要求手机号、企业信息或加好友。

品牌用户获得轻松的参与感；企业用户获得明确的行动启发。权益和内容与业务相关，比无差别现金抽奖更有利于减少低质量参与。

### 3.2 分享一份结果，让新用户独立体验

自然传播点是个人结果卡、共同话题和品牌活动，而不是“再拉几人才能领奖”。分享不作为奖励条件，不按转发次数增加奖励，不做多级分佣。每位进入者都能独立完成完整流程。

建议保留“一跳邀请归因”：辨认本次到达来自哪张邀请卡，用于衡量内容传播效果。首期不构建完整社交图谱，不读取好友列表或群成员。

### 3.3 客户信号可解释，业务意向不由游戏表现推断

把主动表达、游戏行为、身份确认、营销授权、企微关系和销售确认分别记录。翻牌速度、错误次数、分享次数都不能证明用户的预算、职级或购买意向。

“兴趣：咖啡时光”来自用户主动选择；“已完成互动”来自游戏事件；“企微已连接”来自经过验证的回调。结果徽章只是趣味表达，不包装成心理测评或专业诊断。

### 3.4 后台服务运营，前台服务用户

运营人员关心主题、渠道、权益、客户旅程和转化；消费者关心怎么玩、得到什么、是否需要提供信息。游戏界面不出现客户评分、埋点、接口、SCRM 同步等后台概念。

## 4. 用户体验与游戏规则

### 核心玩法

1. 进入活动：展示标题、预计体验时长、活动规则、可选权益。
2. 选择兴趣或课题：单选，可跳过，可更改；不含敏感资料。
3. 开始翻牌：六张卡，随机位置，每次翻开两张。
4. 匹配三组卡牌：品牌模板配相同主题；B2B 模板配课题与方法。
5. 查看结果：获得与主动选择相匹配的徽章；未选择则展示通用徽章。
6. 自愿下一步：领取权益、查看清单、预约、联系顾问或分享结果。

不设置强制倒计时，不因翻错扣减权益，不要求分享复活。每次体验目标为约 30–60 秒，该时长是设计目标，需上线前由用户测试验证。

### 品牌／门店路径

```text
公众号／门店物料／私域活动入口
  → 翻牌 + 选填兴趣
  → 趣味徽章，结果直接可见
  → 自愿领取体验权益
  → 告知用途 + 验证身份 + 发券
  → 可选企微顾问／到店预约
  → 门店服务端核销
  → 在授权范围内做复购运营
```

权益建议：饮品兑换、限定体验、会员服务、预约体验包。优先选择与实际门店消费相关的权益。库存、有效期、适用门店与使用条件应在领取前展示；活动规则要支持异常申诉与客服入口。

### B2B 路径

```text
行业文章／线上会议／官网微信入口／员工自愿分享
  → 课题与方法配对 + 选填当前课题
  → 课题徽章，结果直接可见
  → 自愿领取增长行动清单
  → 最小必要身份验证
  → 自愿补充企业／角色／采购周期，或直接预约
  → ICP 与意向分别评估
  → 顾问接受线索，确认时间与问题
  → SQL／商机／成交回写
```

免费清单应提供实际内容，不能只是留资诱饵。企业、职能、角色、规模、采购周期采取渐进收集；没有可靠信息就标为“未知”，不让游戏推断。主动预约可直接转给服务团队，但不自动等同于销售认定的 SQL。

### 异常与退出

| 状态 | 用户侧处理 | 后台处理 |
| --- | --- | --- |
| 不同意营销推荐 | 仍可使用已经获得的活动权益 | 不进入促销培育旅程 |
| 未授权身份 | 保留匿名体验与结果 | 不伪造客户或手机号 |
| 权益库存不足 | 领取前明确告知，不继续承诺 | 活动暂停发券或启用预先批准的替代方案 |
| 重复领取 | 展示已领取的原权益 | 以租户＋活动＋权益＋主体为唯一键，幂等返回 |
| 网络中断 | 提示重试，不让用户重复提交 | 去重、状态恢复、异步补偿 |
| 重复或延迟回调 | 不重复发券、不重复加分 | 校验签名、事件去重、乱序保护 |
| 推荐授权撤回 | 保留必要的活动服务说明 | 停止后续营销任务，保留必要审计证据 |

## 5. 腾讯生态的载体选择

“腾讯生态小游戏”可指业务上的轻游戏，也可指微信官方“小游戏”技术产品。两者不能混为一谈。本需求以获客与 SCRM 承接为主，建议先验证轻游戏业务路径，再确定最终发行载体。

| 载体 | 适用情况 | 主要取舍 | 本方案建议 |
| --- | --- | --- | --- |
| 微信内 H5 轻游戏 | 公众号内容、活动链接、二维码入口，快速验证 | 无需先发布小游戏包；分享、OAuth、域名与浏览器限制需实际验证 | 首期推荐候选，当前 Demo 使用此形态 |
| 服务型小程序内的轻互动模块 | 已有品牌小程序，需要会员、权益与长期复访 | 需符合小程序定位、类目与审核要求，不能假定游戏内容必然获批 | 已有成熟会员小程序时优先评估 |
| 微信官方小游戏 | 需要长期游戏运营、游戏发现与更深玩法 | 主体、类目、审核、身份与承接能力按小游戏规则逐项验证 | 本项目首期不默认采用；若指定，需单独做可行性验证 |

不能保证 H5、小程序、小游戏之间具有相同的手机号授权、支付、分享、外链跳转或企微承接能力。正式选型前，用企业实际账号验证“入口 → 体验 → 身份 → 权益 → 顾问”的完整链路。

建议渠道分工：

- **公域／内容入口**：公众号文章或菜单、内容活动页、允许的广告入口、线下二维码。视频号等入口以具体账号与内容形式支持的能力为准。
- **私域／服务入口**：企业微信联系我、员工服务、已运营社群、已有会员入口；添加、入群和触达均需用户主动动作及平台允许。
- **自愿传播入口**：活动结果卡、微信会话分享、允许使用的海报。分享参数仅用短期、不可猜测的邀请令牌，不放姓名、手机号或企微标识。

微信 JS-SDK 的分享配置或分享按钮点击不提供可依赖的“成功转发”业务证据。以可验证的被邀请用户到达、后续身份和业务转化做衡量。

平台规则需在实际开发时核对官方文档；当前并未完成这些规则的逐条上线审核。官方参考入口：[微信网页开发](https://developers.weixin.qq.com/doc/offiaccount/OA_Web_Apps/Wechat_webpage_authorization.html)、[微信小程序](https://developers.weixin.qq.com/miniprogram/dev/framework/)、[微信小游戏](https://developers.weixin.qq.com/minigame/dev/guide/)、[企业微信开发](https://developer.work.weixin.qq.com/document/)。

## 6. 在 BesChannels 中如何融合

### 建议的信息架构

新增「营销活动 → 互动获客」，沿用现有后台的账户、权限、活动与客户体系。Demo 中为帮助评审集中展示了四个视图，实际开发时不必重复建设已有模块。

| 模块 | 功能 | 对现有系统的关系 |
| --- | --- | --- |
| 活动工作台 | 业务模板、主题、卡牌、渠道、权益、时间、库存、预览、草稿与发布 | 新增活动类型；发布复用现有审批流程（如有） |
| 客户旅程 | 身份状态、兴趣来源、参与记录、授权、企微关系、承接人 | 优先嵌入现有客户详情页，不建第二个客户库 |
| 增长分析 | 参与漏斗、邀请到达、渠道效率、权益核销、销售转化 | 复用现有报表能力；没有的指标再补充 |
| 接入配置 | 数据映射、角色权限、事件、回调、重试与告警 | 仅管理员可见；Demo 用方案视图说明 |

### 活动配置建议字段

- 基本信息：租户、活动 ID、模板版本、活动名称、服务方、负责人、起止时间、时区。
- 游戏内容：六张卡、三个配对规则、结果名称与文案、品牌色、素材与无障碍文本。
- 渠道：渠道 ID、子渠道、门店／销售／内容资产标识、邀请令牌规则。
- 权益：权益 ID、库存、有效期、适用门店、兑换条件、每人领取上限。
- 授权：服务告知版本、必需字段、营销授权选项、数据保留策略。
- 客户承接：标签映射、行为评分、企微入口、负责团队、自动化旅程。
- 状态：草稿 → 校验 → 待审批（如适用）→ 生效 → 暂停／结束 → 归档。

### 技术融合策略

运营端优先扩展现有前端应用的活动页面；游戏端独立部署在经批准的活动域名。通过适配服务调用确认过的 SCRM 接口，避免前端直接握有系统密钥。

若现有系统支持自定义菜单或 iframe，可用 iframe 作为第一期后台入口，但必须确认登录态、CSP、`frame-ancestors`、Cookie 策略、受限 `postMessage` 来源与令牌交换。若不支持，则使用原生页面扩展或明确的外部活动工作台链接，不假装已经嵌入。

推荐交互边界：

```text
运营人员 → SCRM 已有登录与权限 → 互动活动配置
                                    ↓ 发布活动版本
微信用户 → 活动 H5 → 游戏／身份／权益 API
                         ↓
                 接入适配层 + 事件队列
                         ↓
        SCRM 客户／标签／旅程／企微关系／销售承接
                         ↑
              核销、企微、预约、销售的验证回调
```

不因新增轻游戏引入不必要的复杂微服务。可先使用一个活动服务、关系数据库和现有任务队列；仅在容量与隔离需求出现时拆分。

## 7. SCRM 数据模型与身份关联

| 对象 | 建议字段 | 说明 |
| --- | --- | --- |
| 活动 | tenant_id、campaign_id、template_version、status | 所有数据以租户和活动隔离 |
| 游戏会话 | visitor_id、session_id、source、start_at、complete_at | 匿名随机标识；不视为稳定跨设备身份 |
| 客户关联 | contact_id、provider、appid、external_ref、verified_at | 必须有可验证的映射依据；关联历史事件留审计 |
| 授权凭证 | purpose、notice_version、status、captured_at、revoked_at | 活动服务与营销推荐分开记录 |
| 行为事件 | event_id、event_type、occurred_at、received_at、attributes | 客户端事件不能代替发券、核销与关系确认凭证 |
| 兴趣标签 | label、source、evidence_event_id、updated_at、expires_at | 自报标签保留来源；支持更改与过期 |
| 邀请到达 | invite_token_id、referrer_session_id、referred_session_id | 仅一跳来源，不把令牌当作客户身份验证 |
| 权益 | benefit_id、claim_id、status、expires_at、redeemed_at | 库存与领取使用服务端事务控制 |
| 销售承接 | owner_id、lead_status、accepted_at、opportunity_id | MQL／SQL／商机与游戏事件分离 |

身份规则：

1. `openid` 的范围取决于具体应用，不能直接跨应用当作同一客户；只有满足平台条件且实际返回时才能使用 `unionid`。
2. 企业微信 `external_userid` 不能默认与公众号身份直接等同。依赖平台支持的映射条件、经验证的账号绑定或明确的已验证资料关联。
3. 手机号等个人资料如确需收集，应经明确告知并验证。不能仅凭未经验证的号码字符串合并客户，避免误合并、重复号码与身份冒用。
4. 昵称、头像、兴趣、共享设备或游戏成绩均不能作为可靠合并依据。
5. 匿名转实名后，只有属于该会话且符合用途的事件才能归并。不同租户禁止交叉合并；冲突进入人工处理。

Demo 为了展示界面变化，用预设虚拟身份模拟关联，没有实现真实身份验证。

## 8. 事件、评分和自动化

### 建议事件字典

| 事件 | 触发条件 | 可用于什么 | 不能代表什么 |
| --- | --- | --- | --- |
| page_view | 活动实际载入 | 渠道到达与匿名访客 | 有效客户 |
| preference_submit | 用户主动选择／更改兴趣 | 自报标签 | 经验证的购买能力 |
| game_start | 用户开始游戏 | 参与统计 | 领取或授权 |
| game_complete | 服务端认可的完成状态 | 完成率、低权重互动分 | 采购意向或真实成交 |
| share_intent | 打开分享入口 | 分享功能使用率 | 成功转发 |
| referral_visit | 经校验邀请令牌的好友到达 | 一跳推荐来源 | 新增实名线索 |
| identity_linked | 身份校验及关联成功 | 客户建档和去重 | 同意营销 |
| reward_claimed | 服务端发放权益成功 | 领取、后续权益服务 | 已到店／已核销 |
| wecom_entry_click | 点击企微入口 | 服务入口使用率 | 添加成功 |
| wecom_contact_confirmed | 有效企微回调及映射 | 已确认的私域关系 | 允许无限营销 |
| appointment_requested | 用户主动提交预约请求 | 明确的服务意向 | 已确认到访或 SQL |
| benefit_redeemed | 门店核销接口确认 | 真实权益使用 | 必然是新客 |
| lead_accepted | 销售确认接受线索 | SAL／SQL 流程依据 | 已成交 |
| opportunity_updated | 销售系统确认商机状态 | 商机和成交归因 | 仅由游戏生成的预测值 |
| marketing_consent_revoked | 用户撤回后续推荐授权 | 停止营销、审计 | 必然删除所有必要交易记录 |

### 行为评分与 ICP 分开

Demo 的示例行为分：完成游戏 +5、领取权益 +10、主动预约 +30，每项每个活动只计一次，最高 45。分享、邀请人数和翻牌速度不增加意向分。

正式 B2B 需要另设适配分：例如目标行业、可验证的公司类型、服务范围、角色等；权重由销售团队结合历史成交校准。没有信息就保持未知。

MQL 可以试行“身份已验证 + ICP 达标 + 明确需求或行为意向达标 + 符合适用联系依据”的规则；示例阈值必须通过实际数据校准。主动预约应即时承接，但需销售确认问题、适配与下一步，才进入相应 SQL 阶段。

### 自动化示例

| 条件 | 建议动作 | 退出或限制 |
| --- | --- | --- |
| 品牌权益领取成功 | 在允许的渠道提供权益与使用说明 | 不自动加入促销群 |
| 领取未核销 | 按告知范围与渠道能力提示权益有效期 | 核销、到期或用户拒绝后停止 |
| B2B 领取清单且同意推荐 | 进入与自报课题相关的内容培育 | 撤回、退订、转入销售跟进时停止或抑制 |
| 主动预约 | 分配负责人，创建服务跟进任务 | 按组织约定 SLA；避免重复分配 |
| 回调确认企微关系 | 更新关系，关联活动来源 | 不把已存量关系重复计为私域新增 |
| 销售退回线索 | 记录原因，决定停止或继续允许的培育 | 遵守授权与触达频率，不无限循环 |

本 Demo 不向真实微信用户、企微员工或客户发送任何消息。

## 9. 自愿传播与渠道归因

### 首期传播设计

- 结果卡：展示徽章、活动标题、简短自我表达与活动入口。
- 好友新体验：打开后进入自己的游戏，不继承邀请人的答案或客户资料。
- 同场景话题：品牌围绕周末、门店节庆；B2B 围绕行业活动或常见课题。
- 不做首期的项目：付费抽奖、强制转发、好友数量领奖、多级收益、虚构排行榜、授权前读取通讯录。

### 归因口径

建议同时保留首次来源、最近有效来源和本次邀请来源，避免覆盖原始公域渠道。运营报表默认使用“活动周期内首次有效到达”，其他归因模型独立展示。

建议首期采用活动开始至结束的归因窗口，活动结束后留一个明确的业务转化观察窗，例如 30 天；具体时长由业务确认。每条报表标明窗口、去重方法和更新时间。

访客人数以匿名会话标识做近似去重，识别后可按稳定客户 ID 去重。不得宣称匿名跨设备访客完全去重。新客、私域新增与既有客户必须对照历史客户库判定。

一跳有效推荐系数可定义为“由推荐到达且满足所定义有效条件的新增用户数 ÷ 具备分享机会的用户数”，或拆解为“人均有效邀请到达 × 邀请到达后的有效转化率”。必须统一分母与窗口，不能用分享按钮点击量冒充传播人数。

## 10. 指标体系与实验

| 层级 | 品牌／门店 | B2B |
| --- | --- | --- |
| 体验 | 到达、开始率、完成率、退出位置、匹配错误率 | 同左；另看用户是否理解课题卡 |
| 传播 | 分享意向、有效推荐到达、推荐到达的完成率 | 同左；不默认企业用户愿意公开分享需求 |
| 身份 | 验证后客户数、原有会员占比、营销同意率 | 验证后线索、公司／角色资料完整度 |
| 私域 | 回调确认的新关系数、关系绑定率 | 新关系数、顾问触达与预约接受 |
| 转化 | 实际核销人数、核销率、新客比例、复购 | ICP 匹配、MQL、销售接受、SQL、商机、成交 |
| 成本 | 每个经验证新客成本、每个核销新客成本 | 每条销售接受线索成本、每个商机成本 |
| 质量 | 重复领取、异常账号、权益投诉与退款 | 虚假身份、重复线索、销售退回原因 |

完成率 = 完成人数／开始人数；领取率 = 已验证领取人数／完成人数；核销率 = 核销人数／已领取人数。企微确认与预约是并列分支，不应串成必须逐级递减的漏斗。

成本应包含投放、实际消耗的权益、活动执行和相关开发／运营摊销，不能只用广告费用得到“获客成本”。活动归因不等于因果增量。

建议首轮 A/B：相同渠道、权益与受众，比较“普通权益落地页”和“轻游戏落地页”；核心指标用验证后的新客或销售接受线索，而非只看停留时长。预先设定样本量、观察窗、最小可检测差异与停止规则。当前没有历史数据，因此不承诺提升百分比。

Demo 中统计的是当前浏览器中的模拟会话，没有虚构万人访客、转化增长或收入案例。

## 11. 建议 API 契约与集成要求

以下均是**拟新增活动服务的内部接口示例**，不是在目标系统中已验证存在的 URL。

| 示例接口 | 作用 | 核心约束 |
| --- | --- | --- |
| GET /interactive/v1/campaigns/{id} | 获取已发布活动配置 | 仅下发公开字段，校验活动状态与版本 |
| POST /interactive/v1/sessions | 创建匿名活动会话 | 绑定租户、活动与短期令牌 |
| POST /interactive/v1/events | 上报游戏及偏好事件 | 允许名单校验，事件 ID 去重，限制速率 |
| POST /interactive/v1/identity-links | 验证后关联客户 | 不信任前端传来的任意 contact_id |
| POST /interactive/v1/claims | 领取权益 | 校验资格，事务减库存，幂等键，返回已有领取 |
| POST /interactive/v1/appointments | 登记预约意向 | 用户主动确认；去重与负责人分配 |
| POST /interactive/v1/invitations | 生成邀请令牌 | 不含个人资料，签名与过期策略 |
| POST /interactive/v1/callbacks/wecom | 接收经授权的企微事件 | 按企业微信规范验签、解密、过滤、映射 |
| POST /interactive/v1/consents/revoke | 撤回后续推荐授权 | 撤销待执行任务并传播至相关系统 |

事件示例：

```json
{
  "schema_version": "1.0",
  "event_id": "evt_demo_001",
  "event_type": "preference_submit",
  "campaign_id": "cmp_demo_001",
  "session_id": "session_random_token",
  "occurred_at": "2026-11-21T15:00:00Z",
  "attributes": {
    "selected_topic": "sales_collaboration",
    "source": "user_declared"
  }
}
```

服务端根据鉴权会话确定 `tenant_id`、活动和客户身份，不能信任客户端随意传入的租户或客户 ID。服务器另记录接收时间。匿名事件、授权凭证与关系确认分开存储，按字段最小化传输。

系统集成必须确认：

1. 目标环境是否为可用于联调的测试租户；域名中含 `stg2` 仅是线索，不能代替环境确认。
2. 是否支持自定义活动类型、页面扩展、菜单或 iframe；是否提供沙箱租户与测试账号。
3. 客户查找、创建、更新、标签、事件写入的真实 API 与额度；批量能力和限流规则。
4. 现有 SSO、RBAC、字段级权限、租户隔离与审计要求。
5. 企微应用授权、企业 ID、外部联系人回调、关联字段和跨主体限制。
6. 优惠券／会员／POS 的归属与核销接口；B2B 的线索、销售与商机接口。
7. 域名、公众号／小程序主体、JS-SDK／OAuth 权限、隐私协议和发布审核条件。
8. 自动化触达渠道的权限、消息类型、频率限制、退订与撤回机制。

生产稳定性：事件允许重试但须幂等；失败队列可追踪和重放；发券与库存操作需原子性；企微回调需验签防重放；对异常短时批量领取限速，必要时增加低打扰验证；前端小游戏通关不可成为唯一领奖可信依据。

## 12. 视觉与交互方向

后台延续公开主题的珊瑚橙，并采用白色工作面、浅灰背景、紧凑的信息结构。游戏使用浅紫背景与可翻转的卡牌形成独立记忆点，便于在品牌活动中替换主视觉。

| 设计项 | 建议 |
| --- | --- |
| 后台主色 | 珊瑚橙 `#FF724F`，参考目标系统公开样式 |
| 游戏色 | 探索紫 `#6D50CC`、浅紫 `#EEE9FF` |
| 状态色 | 验证绿 `#25745E`；待确认使用中性灰 |

## 13. MVP 范围与实施节奏

### 首期必须交付

- 一个三组翻牌引擎，品牌／门店与 B2B 两套内容模板。
- 活动配置、草稿、预览、版本发布和紧急暂停。
- 微信内体验适配与选定账号的入口、分享、身份联调。
- 匿名会话、主动兴趣、身份关联与授权凭证。
- SCRM 客户／标签／事件接入和最小必要的旅程配置。
- 品牌权益领取与核销；B2B 内容领取与预约承接。
- 企微关系确认与归因（以实际授权能力为前提）。
- 渠道／邀请到达统计、分支漏斗、事件监控与失败补偿。

### 建议暂缓

多玩法商城、复杂排行榜、跨游戏通用积分、深层社交关系、多级奖励、AI 心理画像、自动诊断采购预算、自动生成大量行业玩法。后续根据真实活动效果决定是否增加。

### 排期参考

| 阶段 | 参考时间 | 产出与验收 |
| --- | --- | --- |
| 业务与接口确认 | 第 1 周 | 两类客户旅程、数据字典、API 能力表、载体选择、验收标准 |
| MVP 实现 | 第 2–3 周 | 游戏、配置、身份、权益、预约与事件适配 |
| 真实系统联调 | 第 4 周 | 客户标签、企微确认、核销与销售回传完整闭环 |
| 灰度与效果验证 | 第 5–6 周 | 异常处理、容量测试、小流量对照、运营调整 |

这是接口、账号和业务资料就绪后的参考节奏，不是固定交付承诺。新主体注册、平台审核、SCRM 开放能力采购、会员或 POS 重建不在该时间假设内。

建议团队：产品／设计共同负责人 1 名、前端 1–2 名、后端／集成 1–2 名、测试 1 名，并由现有 SCRM 管理员、品牌运营及销售负责人配合。费用应依据接口清单、部署环境和权益预算估算，当前没有足够信息给出可信固定报价。

### 正式上线验收

- 两个场景均能从真实微信入口完成全流程；拒绝营销授权仍可正常体验和使用必要活动服务。
- 重复请求不重复发券、加分或创建预约；并发领取不超发。
- 不同租户、账号和角色不能互读客户数据；活动配置与密钥不泄漏到公开端。
- 只有经验证的身份和回调能够改变客户关系、权益与业务转化状态。
- 撤回授权后，相关待执行营销任务及时停止，留下可追踪记录。
- 核销／销售状态与业务系统对账一致；报表明确归因窗口与去重口径。
- 按预计峰值验证性能并预留余量；没有流量基线时先做容量评估，不能空口承诺并发量。
- 由实际账号主体完成隐私告知、平台规则、内容与活动发布的必要审核。

## 15. 下一步启动所需输入

方案评审后，进入实施主要需要：测试租户的适当访问方式与 API 文档、品牌和业务内容、公众号／小程序／企微主体与权限清单、权益与核销系统信息、B2B 有效线索定义及销售跟进规则。提供给开发团队的测试凭据应通过安全渠道管理，不放入前端代码或活动链接。
