# 默契找茬局 · 接口与数据

## 信任边界

身份来自 `cloud.getWXContext().OPENID`。客户端提交的分数、邀请人身份、手机号和合拍结果均不能替代服务端事实。手机号只由微信一次性 code 在服务端换取。数据库客户端读写关闭。

活动服务 `campaign` 和服务端同步任务 `scrm-dispatch` 延续独立授权、事务、幂等和同步队列设计。当前活动 ID 为 `spot-buddy-2026`，新会话采用找茬事件格式；不要复用历史项目策略游戏的会话。

## 云调用

调用形如 `wx.cloud.callFunction({name:'campaign',data:{action,payload}})`。成功返回 `{ok:true,data}`；业务失败返回 `{ok:false,code,message}`。未知错误不向客户暴露堆栈或上游响应。

| action | 输入 | 结果与约束 |
| --- | --- | --- |
| `visitCampaign` | `campaignId`，可选 `inviteToken` | 活动公开配置；首次来源固定；有效非本人邀请码还返回好友同关摘要 `seed/level/foundCount/inviteToken`，不提前公开好友发现顺序 |
| `startChallenge` | `campaignId/requestId`，可选 `level/inviteToken` | `sessionId/seed/level/expiresAt`；邀请码有效则沿用邀请人已完成对局的关卡与难度，忽略客户端自选 seed；每天默认 30 局 |
| `finishChallenge` | `sessionId/moves` | 重放本人事件后计算成绩和推荐难度；如果来自好友挑战，读取服务端邀请人的结果再计算 match |
| `createInvite` | `campaignId/sessionId` | 必须为本人已完成对局；邀请码绑定这个固定对局，后续新局会生成新 token |
| `claimBenefit` | `campaignId/sessionId` | 玩完即可领取；可以未找齐；每活动每人一份；不要求分享或手机号 |
| `getPromotionStats` | `campaignId` | 本人邀请带来的独立到访、完成、领取、主动申请人数；用于后台能力，客户主流程不展示销售漏斗 |
| `requestConsultation` | `campaignId/topic/serviceConsent/privacyVersion/phoneCode/marketing/shareRecap`；选择附记录时加 `sessionId` | 一条本人主动联系申请；手机号从微信验证；营销与附记录默认关闭 |
| `getMyActivity` | `campaignId` | 本人的小礼物、最近 10 张合拍卡、申请、同步与撤回状态 |
| `revokeMarketing` | `campaignId` | 撤回本人后续推荐授权并排队同步；本次主动联系申请继续有效 |

## 游戏事件与结果

每局 60 秒、5 个差异、3 档大小。最多 100 个事件，达到上限即结算。相同差异不能重复计分，时间必须单调且不超过 60000 毫秒。

```json
[
  {"type":"tap","id":4,"at":3200},
  {"type":"hint","at":8000},
  {"type":"tap","id":8,"at":11000},
  {"type":"end","at":60000}
]
```

- `tap`：id 为画面中的 0–11 号物体。正确则加入发现顺序，错误则累计一次点错。
- `hint`：记录使用次数，每次扣 15 分，最多 3 次。提示仅辅助寻找，不替用户记为找到。
- `end`：主动揭晓或到时结束。找齐 5 处时自动终局。
- 计分：找到数 ×100；找齐时加剩余整秒；每次提示减 15，每次点错减 5，最低 0。
- 服务端将最后一条事件时间与服务器已过去的时间作合理性检查（允许 2 秒误差），拒绝超前计时。事件必须终局；相同已完成记录重试返回同一结果，篡改已提交记录返回冲突。

返回结果含 `seed/level/status/found/hints/misses/elapsed/score/nextLevel/advice/match`。`found` 按真实点击顺序排列。合拍结果需要双方各找到至少 3 处：前三处交集占比贡献 80 分，首个相同贡献 20 分；双方关卡或难度不同不计算。仅作游戏趣味结果。

客户端代码可被分析，静态图片答案也能被读取，本实现不是有价奖品的反作弊系统。当前领取的是低风险内容小礼物，不把分数作为现金发奖依据。

## 邀请与归因

正式模式：24 位随机 token → 服务端 inviter + campaign + session → 好友同关 → 服务端重放后比较。不通过客户端传 inviter、score 或 hostFound 来确定正式数据。

演示模式：`duel=seed_level_order`，例如顺序以 0–b 表示 12 个物体；解析器验证 seed、档位、唯一性及是否为该图的差异。链接可跨设备使用，但属于自报数据。正式云服务忽略 `duel`，只认服务端 token。

`scene=i=<token>` 的短参数入口仍支持微信小程序码。生成小程序码需 AppID 与官方接口，当前没有伪造二维码。首次到访归因不被后来的邀请覆盖；自己邀请自己、重复到访不会计新客。

## 数据库

| 集合 | 关键内容 |
| --- | --- |
| `ua_campaigns` | 品牌、活动期限、租户、gameKind、小礼物内容、咨询主题与隐私版本 |
| `ua_visitors` | hash(活动, OPENID)，首次邀请来源、首次完成、每日开局数量、最近 10 张合拍卡 |
| `ua_sessions` | 本人身份、seed、level、friendSessionId、期限、已验证结果与事件签名 |
| `ua_invites` | 随机 token、本人、活动、固定 sessionId、失效日期 |
| `ua_claims` | hash(活动, OPENID)，已领内容快照 |
| `ua_leads` | 验证后手机号、主题、独立授权、版本与时间 |
| `ua_stats` | 活动总计或邀请人维度的四项独立人数 |
| `ua_outbox` | 待同步事件、租约、尝试次数、下次重试时间 |

库存为 null 时不限制数字内容领取；数值库存的扣减和领取记录、统计及 outbox 在同一事务写入。数据库与手机号只开放给受控云函数，不记录完整电话或授权 code 到日志。

## SCRM 适配协议

用户给出的 BesChannels `/dashboard` 是管理页面，不是已知写入 API。项目方需实现 HTTPS 适配服务，并依据厂商文档映射联系人、活动与授权字段。

配置云函数环境变量 `SCRM_ENDPOINT`、`SCRM_AUTH_TOKEN`、`SCRM_TENANT_ID`。令牌不进入前端。一个同步部署对应一个租户，更多租户需独立环境或服务端路由。

发送方式：POST JSON，`Authorization: Bearer <token>`，`Idempotency-Key: <eventId>`。

```json
{
  "schemaVersion":"1.0",
  "eventId":"lead_<participant-hash>",
  "tenantId":"your-tenant",
  "campaignId":"spot-buddy-2026",
  "type":"consultation.requested",
  "occurredAt":1795392000000,
  "data":{
    "participantId":"<opaque-hash>",
    "phone":"<server-verified-phone>",
    "topic":"了解产品体验",
    "serviceConsent":true,
    "marketing":false,
    "privacyVersion":"published-version",
    "consentAt":1795392000000,
    "recap":null,
    "attributionId":"<inviter-hash-or-null>"
  }
}
```

接收成功需要 2xx 和 `{accepted:true,eventId:<同一个事件ID>}`。适配服务必须已可靠持久化，不是收到后直接丢弃。界面“服务方已接收”不等于销售已经联系。

事件类型：`benefit.claimed` 只写参与记录，不自动创建可营销线索；`consultation.requested` 按验证手机号匹配/创建联系人及自愿主题；`consent.revoked` 撤回该活动授权。选择附记录时 recap 只含得分、找到数量、用时与提示次数，未选择时为 null。

无配置时保留 pending。每分钟最多处理 5 条，单条总超时 8 秒、租约 60 秒，至少一次投递，接收端按 eventId 去重。失败从 30 秒指数退避，上限一小时，第八次失败进入 dead。

撤回事件等待对应联系申请已接收后发送；等待时延后检查，避免堵塞整批。前序 dead 则标记 DEPENDENCY，人工修复应先恢复申请，再恢复撤回。修复时保持原 eventId。

未实现自动数据清理、生产告警和管理端。上线前由运营方确定保留期限、删除申请渠道和人员权限。游戏合拍与得分不可转成采购意向标签。
